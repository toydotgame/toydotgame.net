Bringing Open-Source Software Back From the Dead, or how I Fought Time for a Couple JAR Files

Written: 2025-07-15 · Last Updated: Never

You may have read my article from a year ago, specifically the section on Wolvereness' DMCA of the CraftBukkit and Spigot codebases (or you'd know this from wherever else—it's not a niche bit of old Minecraft sysadmin knowledge by a long shot). The end result of this is that early 1.7 and prior Spigot releases are effectively all lost media. If you'd like to run a server with an old Spigot server JAR from that time, let alone develop using the Spigot API JAR, you'll need to rely solely on now-11-year-old links and the popularity of your specific Minecraft version to get by.

For me, that wasn't a problem. I ran a Spigot 1.6.4 server and wrote a plugin for it too, so I was able to find a server and API JAR despite the DMCA. This is called pure luck because of 1.6.4's immense popularity (at least until 1.7.10, 1.8.9, and 1.12.2 shattered that).

The legality of this​/DMCA TL;DR

#Not​Legal​Advice​Im​Just​Some​Loser​Who​Plays​Minecraft

I believe the DMCA (which is what I will henceforth refer to it as) boiled down to this:

  • Spigot is patch-based, and as such includes a few lines of Mojang's Mineacraft server code as an indicator to the patch applicator where the patch should be applied
  • The Spigot additions are property of the Spigot contributors, licensed as LGPL
  • The Minecraft server code is property of Mojang, licensed under the Minecraft EULA/proprietary license
  • Given the Bukkit and Spigot repositories therefore contains bits of Mojang-licensed proprietary code, this means Bukkit and Spigot are distributing Mojang's code. This also means their own additions (licensed and copyright-owned under the LGPL by contributors) is being unlawfully included in the Mojang-copyrighted code

This means that this code, including Wolvereness' own contributions (LGPL licensed and owned by him) had their copyright violated under these distributions.

THIS MEANS THAT SpigotMC cannot distribute the compiled binaries, as it breaches Wolvereness' copyrights, given he wrote and released his code under the LGPL license, yet it's being distributed under Mojang's EULA and copyright.

This lack of available binaries makes stuff hard. Additionally, the Spigot project used GitHub at this time, AFAIK. GitHub is a problem due to the fact that the original DMCA request was placed on that platform and nuked the original repositories of Spigot code.

As a result of this, SpigotMC does not support nor have facilities in place to distribute these DMCA'd server versions—making them really, really damn hard to find.

PLEASE DO NOT DISTRIBUTE THE BINARIES YOU CREATE AS A RESULT OF FOLLOWING THE INSTRUCT​IONS YOU FIND BELOW

Doing so is a direct violation of the DMCA. These binaries include code built on and including patched Minecraft classes. From the moment you run ./applyPatches.sh, you will have a working directory that is not fit for distribution thenceforth!

Copyright notice regarding where we're getting this from

We will download code from the following locations:

  • SpigotMC Stash: This holds the current Spigot code. It does not contain any Mojang code that would trigger the DMCA
  • GitHub:[Bukkit GitHub repo] These sources are for a standalone library Wolvereness made (a dependency of Spigot's API, IIRC), and the Bukkit API (which contains no Minecraft code)
  • repo.md-5.net: This contains only Minecraft code, and no Bukkit contributor code, despite being labeled as an org.bukkit package. No Bukkit API exists in it, and so I can only assume it is devoid of LGPL and community-owned code. Therefore, it does not violate the DMCA

Now lets get us some 1.6 stuff! We're gonna be fighting lots of ancient code and workflows, so be prepared. You will require:

  • Go ≥ 1.23
  • Maven ≥ 3 I'm assuming. Just stick to latest and you'll be fine
  • JDK 8 Maybe ≥ 6 will work, given Minecraft at the time targets that, but I used OpenJDK 8 and was fine
  • POSIX shell (e.g. Bash, Zsh, Fish, the macOS terminal) You can use Windows with Git BASH or WSL or whatever, but not Command Prompt or PowerShell

Tutorial

    Part 1: Getting stuff

  1. First, clone Spigot from where it lives nowadays: 
    git clone https://hub.spigotmc.org/stash/scm/spigot/spigot.git && cd spigot/
    Wherever you cloned and have this spigot/ directory, I will henceforth just call it spigot/.
  2. Then, we need to checkout the last 1.6 version: 
    git checkout 71d3b3b5ad6ffe5d74a98f563d9a36ee073ed7ed
  3. This repository uses Git submodules. However, it depends on Bukkit and CraftBukkit. Bukkit lives/lived on GitHub, and is still there (because it's not DMCA-infringing, see above); however, CraftBukkit was zapped. Therefore, we need to use the modern CraftBukkit repository instead of the old, DMCA-infringing one.
    Modify .gitmodules in the root of your spigot/ repository directory and replace the following line: 
    [submodule "CraftBukkit"]
	path = CraftBukkit
-	url = https://github.com/Bukkit/CraftBukkit.git
+	url = https://hub.spigotmc.org/stash/scm/spigot/craftbukkit.git
  4. Let Git fetch our desired versions of the now-configured submodules. It'll figure it all out. 
    git submodule update --init
    Git will get bingled on fetching the CraftBukkit repo, because the GitHub CraftBukkit and SpigotMC stash repos are not the same thing entirely (so and so not DMCA'd code, as above…). Therefore, we need to manually check out the last 1.6.4 commit: 
    cd CraftBukkit/

git checkout ff8b70fbb7a96b9d2ff078afcf3b3ff90f200981 && cd ../
  5. Apply your patches!

    Henceforth, your spigot/ directory will be a violation of the DMCA if you publish it online.

    ./applyPatches.sh

    6. Part 2: Bodging it to work 11 years later

  6. If you're using a relatively modern (not 2013-era) version of Maven, HTTP repository requests are blocked by default for security purposes. You must use HTTPS in your POMs. For this tutorial, we'll instead be bodging Maven to not block HTTP. This is insecure, and you should not do this in any other case!
    Add the following to ~/.m2/settings.xml:
    If you already have a Maven settings file, just add the <mirror> entry to your existing config 
    <settings xmlns="http://maven.apache.org/SETTINGS/1.2.0"
          xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
          xsi:schemaLocation="http://maven.apache.org/SETTINGS/1.2.0 http://maven.apache.org/xsd/settings-1.2.0.xsd">
    <mirrors>
        <mirror>
            <id>maven-default-http-blocker</id>
            <mirrorOf>external:dont-match-anything-mate:*</mirrorOf>
            <name>Pseudo repository to mirror external repositories initially using HTTP.</name>
            <url>http://0.0.0.0/</url>
            <blocked>false</blocked>
        </mirror>
    </mirrors>
</settings>

  7. OverMapped

    Now we need to set up a local copy of Wolvereness' library called OverMapped. It's independent of the Bukkit or Spigot projects, but was used in them for building certain stuff. It used to be on Maven Central, but today it isn't. Spigot-API requires version 0.0.2, so we will check out that from Wolfe's GitHub: 
    mkdir -p ~/.m2/repository/com/wolvereness/overmapped/0.0.2/ \
&& cd ~/.m2/repository/com/wolvereness/overmapped/0.0.2/

git clone https://github.com/Wolvereness/OverMapped.git tmp/ && cd tmp/

git checkout da90bdcd8dec91e4994f462f21a65c8f1b3f2735

mvn install
    Optionally, you can now remove the source code from your computer. You no longer need it, but you can keep it if so desired (for data hoarding :3); if you'd indeed like to remove it: 
    cd ../; rm -rf tmp/

  8. Minecraft server

    Go back to your spigot/ directory, or some temporary directory. It doesn't really matter where we do this because we can just rm the two files we make at the end. I'll define $TEMP_LOCATION as the URL of the package we're working with for brevity: 
    export TEMP_LOCATION="https://repo.md-5.net/repository/public/org/bukkit/minecraft-server/1.6.4/minecraft-server-1.6.4"

curl -O "${TEMP_LOCATION}.jar" && curl -O "${TEMP_LOCATION}.pom"

mvn install:install-file \
	-Dfile="minecraft-server-1.6.4.jar" \
	-DpomFile="minecraft-server-1.6.4.pom"

rm -f "minecraft-server-1.6.4.jar" "minecraft-server-1.6.4.pom"

  9. AetherClassNotFound errors

    Another thing since the Maven setup in 2013 Spigot is so out-of-date is that Maven 3.1 and above use Eclipse Aether instead of Sonatype Aether. This means you'll probably get/have got ClassNotFoundExceptions for org.sonatype.aether classes/sub-packages.
    As per the wiki article for source 7, we can just do a dumb downgrade of the affected packages in spigot/. (First, cd back to your spigot/ directory)
    For both of these, you'll get failures to refactor/build the Spigot server/API. That's okay, because we haven't run a clean build yet, and so don't have all the libraries. (TL;DR we don't need to worry about it!!!)
    1. maven-dependency-plugin
      Revert to version 2.8, goal tree: 
      mvn org.apache.maven.plugins:maven-dependency-plugin:2.8:tree
    2. maven-shade-plugin
        You could also just run the mvn command for 2.0:shade, and not bodge the POM—but I haven't tested it.
      1. First, bodge the POM for Spigot-Server. Change the following line in Spigot-Server/​pom.xml: 
        		<artifactId>maven-shade-plugin</artifactId>
-			<version>2.0</version>
+			<version>2.1</version>
      2. Then, revert to version 2.1, goal shade: 
        mvn org.apache.maven.plugins:maven-shade-plugin:2.1:shade

      3. Part 3: Building!

    3. You can do any of the below for whichever combination of end JARs you want!:

      • Server and API JARs:

        mvn clean install

      • Sources:

        mvn source:jar

      • Javadocs:

        We gotta add a flag for maven-javadoc-plugin to still build the JAR even if we reach an error (which we get a lot of since the Spigot codebase has tons of Javadoc syntax errors!):

        mvn javadoc:jar -Dmaven.javadoc.failOnError=false

Please remember to undo the Maven HTTP bodge (~/.m2/settings.xml) from earlier if you're ever going to work with Maven again!

Post-script

If you've read my Spigot ArrayIndexOutOfBoundsException blog article or the Spigot Forums post my article is based on, you may know of this bug and its patches. The patches for 1.6.4 for this bug as built binaries are lost to time, but here's their code so you can perhaps revive them (for personal use!!!):

There are multiple patch files named Enable-Improved-Ping-Sending in the spigot/CraftBukkit-Patches/ directory. They were released in this exact order:
  1. 0030, signed off by Aikar, made some time before 1.6.4 Spigot entirely. This code persisted until March 26th, 2014, when the original strike of this bug occurred. This is the version available in your local copy of spigot/.

    This version iterates through the player list using currentTick % numberOfPlayersOnline. currentTick is determined by type-casting from system time (long) down to an int, thus enabling an overflow error where currentTick can become negative
  2. 0024, written by Thinkofdeath, was the first patch for this bug. All it does is replace the call of currentTick with abs(currentTick), meaning negative values get forced positive. Nothing else is changed.

    Thinkofdeath pings Aikar (the original patch author) for a better solution to replace this temporary one
  3. 0124, committed by Thinkofdeath—but probably written either directly by or in association with Aikar—was written a couple days later. Aikar came up with this algorithm: Also, this explanation of the algorithm is more a guess because these are non-static methods and I don't really understand their implementation.
    1. Instead of index = abs(currentTick)%numberOfPlayersOnline, we rename index to currentPing. currentPing is initalised to 0
    2. For each player, when getting their ping, currentPing is set to (currentPing+1)%numberOfPlayersOnline. Mathematically,

      x+1 mod y

      yields a value that will

      ∈[0, numberOfPlayersOnline-1]

      —which, conveniently, if you have a list or array that is numberOfPlayersOnline long, means that currentPing will always be a valid index in that list or array.

      Conveniently again, I've abstracted the names of these variables. numberOfPlayersOnline is actually the #size() value of the player List, and in fact this ping function only uses currentPing as an array index! Meaning it is mathematically impossible for an ArrayIndexOutOfBoundsException to occur! That is, assuming no race conditions or non-Thread-safe code, but Minecraft is single-threaded and also shut up ♥
    So Aikar has removed all calls to currentTick, and additionally has wrapped the entire function in a (redundant) try-catch() for sillies/safety/just in case™. Awesome!

    If you're going to include a patch for this bug, I highly recommend this patch file!

That's it! Thanks for reading!
