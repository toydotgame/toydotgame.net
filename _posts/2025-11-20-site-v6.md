Fortunately, or unfortunately—whichever way you see it—a site that looked like
that was one that got me thinking. Something something CSS and you get the
point, this site don't look too much like v5 any more!

I had designed v5 such that it didn't rely *too much* on HTML5 semantics and
hyper-specific CSS (for the content body at least), and as such the v6 branch
was originally meant to solely be a CSS rewrite. I made a v6 branch for a few
reasons:
1. Each major update to my site comes with a new branch.[^site-versioning] As
   far as Git tracks (since late 2019/early 2020) we've had:[^branch-names]
	* [toydotgames-archive/TheScratchersLtd.github.io](https://github.com/toydotgames-archive/TheScratchersLtd.github.io){:.noexternal}
   	  `master` – v2, even though the commits do say "Update 3.x.y"—it's v2. This
   	  specific Git tree is a continuation of Toydotgam/Toydotgam.github.io, but
   	  that repo is *definitely* lost
	* `master` — v3
	* `main` – v4
	* `v5` — v5
	* `v6-dev` – v6
   
   v1 and v2 are extant, but in the form of ZIP files in my archives
2. Because I honestly didn't know if I'd actually go through with this or not.
   My plan here was to do Aero in CSS, which sounded daunting, and so I wasn't
   even sure if v6 would come to fruition or if it'd be a complete failure lol
3. So I could maintain `v5` with fixes, adding badges, etc. I knew `v6` (whether
   I chose to bring it to fruition or not) would take a while and it'd be
   important to keep `v5` live, maintained, and fully working in that time

[^site-versioning]:
	Ideally the criteria for a major site update *isn't* a full markup rewrite
	(e.g. a simple major CSS overhaul can constitute a major update), but…so far
	*every* major version has been a full overhaul lmao.

[^branch-names]:
	`master` (v3) has since become `v3-master`, and `main` (v4) has since become
	`v4-main`. Also, after I went all-in on v6 and made it the primary branch,
	`v6-dev` became `v6`.

Oh yeah! My plan! I thought frutigeraeroarchive.org looked cool as hell, and my
site v5—being more \[intentionally\] '90s-y—kinda just…wasn't as cool? *I HAD to
have that kewl new Aero look!*

Doing full Aero in a web layout was a scary concept, I'd either have to do CSS
more complex than I'd ever done before, or start messing with getting textures
and crazy layouts to work (eek!). I ended up going with the former.

I started by stashing away the v5 `main.css` and starting completely anew with
the v5 "template" page (which was more of a CSS showcase/reference for myself
than an actual blank template—despite me actually *using it* as a template
still!). At this time, v6 was meant to be a drop-in stylesheet replacement, and
so I had to design it around the `<div>`{:.highlight.language-html}s and IDs I
had already been using (so that I wouldn't need to change a single line of
markup in my now-steadily-growing catalogue of site pages and blog articles).

What I ended up with are the Aero "windows" before you right now.[^pending-time]
I rigorously tested them for responsiveness and nice display down to viewport
widths of something like 40(?) pixels.

[^pending-time]: Assuming I'm still using v6 when you're reading this, that is.

**But then it struck.**{:style="font-variant:small-caps"}

This document markup, despite being designed to *not* be v5-specific because I
*know* I'll never have one design for ever, was still v5-specific enough to irk
me…

Damn.

Would a reasonable response be to change the markup because I have *tens* of
pages (and it's not so bad), and not *thousands* (i.e. *It's low
effort!!!*)?<br>
Yes.<br>
Did I do that?<br>
No.<br>
Did I do the unreasonable thing instead (complete from-the-ground-up port of my
site from static pages to a static site generator that I didn't even know how
to use)?<br>
Uhh…*yeahhh I diddd :ppp…*

As my site grew, the concept of a generator became more and more appealing. I
remember back in 2019 manually writing up my sitemap.xml file and changing the
`lastModified` values literally every single time I changed anything.[^why]

[^why]: Still no idea why I did that.

Also, on that v5-specific markup point from earlier. I already was running into
issues changing my `<head>`{:.highlight.language-html} tag data. I had
`contentloader.js` load in the nav and footer stuff dynamically, but that
1. sucked even for that purpose, and
2. (obviously) couldn't do `<head>`{:.highlight.language-html} data

If I just used Jekyll (or similar!), I could write a bunch of Markdown and
completely fundamentally change the HTML markup at any point, en masse! Which is
the story of how I learned Jekyll *properly*.

<small markdown="1">I did technically use Jekyll for the v3 era, but it was
using some horrid self-modifications of the *Hacker* theme and I know for a fact
I didn't know what I was doing at all.</small>

So…v6 now?<br>
Turned out pretty nice! Having gone to the trenches and back (making the Aero
styles), I had brute-forced improved my CSS skills to the point where the
general v5→v6 design migration process involved now rewriting the Aero CSS
selectors from v5 elements to my new v6 Jekyll-produced layout elements. From
there, I began working on the actual nitty-gritty nav, article body, and footer
content styles (that I hadn't begun yet).

Thanks to the power of Liquid templating my markup, there's a surprising level
of dynamic-ness I can add to a "static" site. For example, I have two Atom
feeds:
* [One for blog articles]({{ site.feed.path }})
* And [one for status updates]({{ site.feed.status_path }})!

The "status" page is another example! It's a Jekyll Collection of miniscule
Markdown files containing a date, list of attachment image(s) (if any) and
some basic text. I can iterate through said set and create [the status index
page](/status) for anyone to view, without me having to do anything for it! I
just make a new text document in that collection and that's it!

I know this is like 20-year-old news for anyone using a static site generator
already (which is most people…), but my goodness it's such a novelty!

So I've mentioned I have Atom feeds and a status page, so I'll rapid-fire off
a bit more that v6 has to offer:
* `X-Clacks-Overhead` actually in the HTTP response instead of
  `http-equiv`{:.highlight.language-html}!
* Automated sitemap (for fun)
* Less garish favicon
* WebP images for common assets (I was a moderate-disliker of WebP up until
  literally the morning of writing this (due to lackluster support in basically
  everything), but seeing how its lossy and lossless compression is literally
  THAT GOOD I don't think I'll ever be going back (given I thought JPEG was
  pretty handy at reducing file sizes)[^webp])
* Markdown format for tons of general markup, and also more cool dynamic stuff
  like footnote and abbreviation definitions inline which Jekyll creates an
  automatically maintained list for (much in the same was I was **manually**
  doing for v5!)
* Randomly-selected background image for the page (using a bit of async JS
  trickery)
* Crazy reliable and more rigorous content styles, not only more but everything
  is just that bit more nicer-looking and responsive
* [HTTP 418 page](/418) :3
* Pixelated rendering for the badges in the footer so they're not blurry
  * Ditto for things like my avatar and the image lightbox modal thingy
* Page turner next/previous buttons for blog articles
* A *Recent blog posts* section that I don't gotta update!
* Microblog (status page). No algorithms!
* More badges than ever before!
* More stuff I'm far too lazy to type up right now.. :p
* Oh also [oneko.js](https://github.com/adryd325/oneko.js){:.noexternal}!!!
  Hiiii kitty!!!!
